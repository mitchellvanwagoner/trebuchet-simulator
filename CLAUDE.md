# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Setup (Windows venv lives in .venv/)
.venv\Scripts\activate
pip install -e ".[dev]"

# Run all tests / a single test
pytest
pytest tests/test_physics.py -k test_name

# Launch the Streamlit web UI (opens browser at localhost:8501).
# Rebuilds .venv automatically if it is missing or stale - a venv records
# absolute paths, so moving the project folder breaks it until this repairs it.
python run.py

# CLI simulation and optimization
trebuchet simulate --arm-length 0.813 --animate
trebuchet optimize --target-distance 30 --lock counter_weight_mass=14
```

There is no linter configured. Saved CLI outputs (GIFs, plots) land in `outputs/` (git-ignored).

## Architecture

Python package under `src/trebuchet_sim/` (src-layout, installed editable). The core dataflow:

`config.TrebuchetParams` → `physics.TrebuchetSimulator.simulate()` → `SimulationResult` → consumed by visualization, web UI, CLI, and optimizer.

- **physics.py** — Euler-Lagrange dynamics of the launch phase (state = `[theta, theta_dot, alpha, alpha_dot, psi, psi_dot]`: arm angle, sling angle, and the counterweight's swing about its pin), integrated with `scipy.solve_ivp` until a release-angle event fires. Produces `SimulationResult` with `distance`, `efficiency`, a `metrics` dict, the `LaunchSolution`, optional energy history, and the post-release `trajectory`. The sling is modeled as a real rope: when the rigid-link tension would go negative the projectile detaches (`LaunchSolution` stitches taut/slack segments) and the re-tension snap dissipates energy, reported as `string_slack_fraction` / `sling_snap_count` / `sling_snap_energy`. Those three only fire once the sling has *already* let go, so `sling_tension_deficit` grades the approach as well: the share of the launch the sling spent below `config.SLING_TENSION_FLOOR` projectile weights, weighted by how far below, clamped to [0, 1] and never less than `string_slack_fraction`. It is the optimizer's only continuous handle on jerk - see `snap_penalty_weight`. The counterweight rope is *still* a rigid link, so it keeps the feasibility-style `min_cw_rope_tension` / `cw_rope_compression_impulse` (∫max(0,−T)dt, N·s) metrics — nonzero impulse means the arm out-accelerates the falling counterweight and that part of the run is unphysical (web UI and CLI warn above the 0.05 N·s noise floor). Both metrics are pulley-machine only; a pinned counterweight has no rope to go slack. The ground is the second one-sided constraint, and it is independent of the sling's, so a launch is a stitched walk through four regimes rather than two - `TAUT` / `SLACK` / `TAUT_GROUND` / `SLACK_GROUND`, since a sling can go slack over a projectile already lying in the dirt and a taut one can drag a projectile along it. `TAUT` keeps the six-component state; the other three carry the projectile explicitly as `[theta, theta_dot, px, py, pvx, pvy, psi, psi_dot]` with the grounded pair pinning `py`/`pvy` to zero, so a resting projectile stays exactly on the line instead of drifting off it. `TAUT_GROUND` is the one regime where both constraint forces are live: `grounded_forces()` solves the sling tension alongside the accelerations, so the sling letting go and the projectile lifting off are each just one of them reaching zero. Landing costs energy - `_apply_ground_impulse` takes the projectile's downward momentum and the sling's share of the jerk together, since a landing on a loaded sling is felt by the arm - reported as `projectile_ground_fraction` / `projectile_ground_contacts` / `projectile_ground_energy`.
- **trajectory.py** — ballistic flight after release with quadratic air drag. Shared so the sim engine, matplotlib animation, and web animation all render the identical flight.
- **`sample_component_positions()`** in physics.py samples projectile/arm-tip/counterweight positions from a solved run; both animation frontends (matplotlib and Three.js) build frames from it so they can never disagree with the physics. It and the energy history read the launch through `LaunchSolution.full_state()`, which resolves a segment and evaluates its interpolant once per instant: the per-quantity accessors beside it each do their own, and a sampler wanting all three paid three times over - 41% of a `track_energy` run.
- **visualization.py** — the matplotlib frontend: the CLI's dual-view animation and `build_energy_figure`, which the dashboard embeds directly (`compact` for the one-screen layout, `dark` applied to a finished figure rather than through rcParams, so the CLI's saved PNGs are untouched). No physics of its own - frames come from `sample_full_timeline`, the energy panels plot `SimulationResult.energy_history` as recorded.
- **optimization.py** — differential evolution over the five optimizable params (`PARAM_NAMES` / `PARAM_BOUNDS`). The objective penalizes counterweight-rope compression impulse (`slack_penalty_weight`, mirrored in both engines) so the search only returns solutions where that rigid link stays in tension. It separately penalizes `sling_tension_deficit` (`snap_penalty_weight`, also in both engines, exposed as `--snap-penalty-weight` and as the dashboard's Tuning popover "Snap penalty"). The two are not redundant: an impulse is identically zero until a rope has let go, so it is a wall and not a gradient, and DE parked on the cliff edge without the deficit term. The objective's weights are calibrated against a benchmark whose targets are 40/70/95% of the range each machine can reach *with the snap penalty active* - a machine is allowed to throw far further by wrecking its own sling (a plain pulley machine reaches 182 m limp against 106 m loaded at the current defaults; the traditional machine pays nothing for the same promise), so targets drawn from the unprotected range would be unreachable by anything worth building. Against those, `distance_weight` 10 against `efficiency_weight` 5 lands within 2% of the target every time, where the old 1 hit 37% and missed by a median 17.9%; `snap_penalty_weight` 1000 over 300 buys a 20x lower tension deficit for 0.008 of mean efficiency. Three parameter tiers matter throughout the codebase: *free* (optimizer searches, between `PARAM_BOUNDS` or a `param_bounds` override), *locked* (user pins an optimizable param), *fixed* (`fixed_params` — never optimizable, e.g. pivot height, projectile mass). Two bounds tables, not one: `PARAM_BOUNDS` is the default search range and `PARAM_LIMITS` the envelope a `param_bounds` override may move within, so a range can be widened past the defaults as well as narrowed. A locked parameter's range is unused rather than an error, because the dashboard carries one for every parameter regardless of its lock. `fastsim.py` models both linkages *and* the same rope-sling launch physics.py does, so neither the machine nor the trajectory decides the engine any more; its state carries the counterweight swing on both, matching physics.py's layout so the two take the same step path rather than merely solving the same equations. Pure computation, no printing; cli.py is the presentation layer.
- **config.py** — `TrebuchetParams` dataclass; derived quantities (masses, moments of inertia, areas) are properties. `DEFAULT_OPTIMIZABLE_PARAMS` is the single source of defaults shared by CLI, web UI, and tests, and is optimizer output for the 30 m target - so it is re-derived whenever the geometry it was searched against moves, as it was when `pivot_height` rose to 2.5 m (the pulley machine's equations of motion do not contain the pivot height, so the old set launched identically and simply released 1.5 m higher, overshooting to 31.37 m). `MachineType` picks the counterweight linkage: `PULLEY` (weight on a rope over the pivot axle, constant lever `pulley_radius`, single-sided arm) or `TRADITIONAL` (weight pinned to the arm's short end `length_counterweight` behind the pivot, so it swings on its own coordinate and the beam has mass on both sides — see `arm_cm_offset` / `moi_arm`). One set of equations of motion covers both; `has_pulley` branches the handful of places they differ. `initial_arm_angle` defaults to `None` and `__post_init__` resolves it per machine from `DEFAULT_INITIAL_ARM_ANGLE`; `counter_weight_rope_length` resolves the same way through `initial_cw_rope_length` - one wrap of the pulley, or the traditional machine's own short arm. It used to be one wrap either way, which sized a pinned counterweight's link from `pulley_radius`, a parameter that machine does not have and whose default moves whenever the *pulley* machine's defaults are re-swept. The traditional defaults are geometry for a machine loaded the way a real one is - tip one sling length up, so the stone lies on the ground at the far end of a sling stretched back behind the pivot - which is why its `release_angle` is -5.016 rather than the -4.94 that was swept when the stone hung from the tip 23 mm underground: the two poses differ by 10.5 degrees of initial sling lean, and the stale angle reads 63.9 m against 70.2 m.
- **fastsim.py** — the Numba engine behind the optimizer's objective, and a port of `physics.py` rather than a simplification of it. It runs the same stitched launch through the same four regimes: taut segments (the Dormand-Prince tableau unrolled into scalars, the hot path a converged design spends its whole launch in) alternating with the three eight-component ones - slack, and the two grounded - which share a single array-based stepper (`_integrate_eight_segment`) branching on a regime code, so there is one readable copy of the tableau rather than three more; joined by the same inelastic `_apply_snap` and `_apply_ground_impulse`. It used to hold the sling rigid and lean on the objective's penalties to keep the search where that lie did not matter, which left the engines a median 56% apart on distance once a sling let go, and let a search pushed hard on distance win on throws only the rigid model believed in. The ground was the same story a step later, and it was closed the same way. They now agree to a median 0.0066% on distance across launches carrying a discontinuity and 0.0012% across quiet ones, and to 0.003% on the energy the ground takes (`tests/test_fastsim.py` measures this over both machines, classifying a launch by whether it contained any discontinuity at all rather than by slack alone - a landing is one too). The two also open every segment on the same step grid: `_initial_step` / `_probe_step` port scipy's `select_initial_step`, where this engine used to start each segment at a fixed 1e-3, and over a short segment that choice is the whole sample. That was the last loose metric's cause - the counterweight rope's compression impulse is a trapezoid over a spike, and it was held to 30% and a 0.25 N*s floor against a fixed opening step; all eleven draws in the sweep that carry any impulse now agree to better than 0.7%, from 0.038 N*s to 66.9. Agreement is still not convergence, and this is the metric where the difference shows: below about 1 N*s neither engine's value is converged - the reference reads 0.635 / 0.571 / 0.605 at rtol 1e-6 / 1e-8 / 1e-12 on the draw that motivated the port, where this engine reads 0.639. It feeds a feasibility term, so what has to agree is that the design is charged out of contention. Closing each gap also opened design space the search had been driven out of: the sling port took the pulley machine's measured maximum range from 121.6 m to 191.3 m, and with the snap penalty at its shipped 1000 the ground port took it from 73.6 m to 88.1 m at the 1 m pivot of the time, because designs that were previously mis-scored - flying the stone through the floor - resolve into real ones.
- **web/app.py** — Streamlit dashboard (3 columns: parameter inputs / animation + energy plot / results). Streamlit reruns the whole script on every widget interaction, so expensive outputs (animation HTML, energy figure) are pre-rendered once in `_store_result()` and cached in `st.session_state`. Results render as custom HTML (`_metric_grid` / `_spec_list` / the hero block), not `st.table`. Unit switching: length inputs swap between separate metric and ft/in widgets so they reseed themselves, but the single-box inputs — masses, and the search-range boxes, which use decimal feet rather than a ft+in pair — must be converted in place by `_sync_unit_inputs()` before any input renders. Search ranges live in a popover: two more boxes per row would not fit the left column, and the one-screen layout has no slack. Whether a range counts as customized is decided at the box's own display precision (`INPUT_DECIMALS`), since a default that has been through a unit conversion and back no longer equals itself in SI.
- **web/theme.py** — the design system, and the single source of truth for the dashboard's look: palette constants, `streamlit_theme_env()` (Streamlit resolves its theme at server start, before the app script runs, so it can only arrive via env vars — applied by both `web/launcher.py` and `run.py`, which is why the container and a local checkout match without a `.streamlit/config.toml`, a path that is git-ignored), and `DASHBOARD_CSS`. The layout is a fixed-viewport flex column: the page is pinned to `100vh` and the panels that should absorb slack are marked `flex: 1 1 0`, replacing the previous `calc(100vh - Npx)` magic numbers that had to be re-measured by hand and had already drifted far enough to push the header off-screen. Imports nothing, so `run.py` can read the palette before the package is installed.
- **web/animation3d.py** — no physics: samples the solved result into a JSON timeline (`_build_timeline`) and embeds a self-contained Three.js HTML page that plays it back with scrub/speed controls. The HTML template is a Python string with `__TIMELINE_JSON__` / `__HEIGHT__` / `__THREE_JS__` / `__ORBIT_JS__` placeholders plus the palette placeholders in `_THEME_SUBSTITUTIONS` (so the scene shares `web/theme.py`'s colors); Three.js r128 is vendored in `web/static/` and inlined so the animation works offline (r128 pinned deliberately — newer releases removed `examples/js/OrbitControls.js`).

Selecting a machine touches every layer, because the two differ in one design variable rather
than in a setting: `config.LINKAGE_PARAM` maps each machine to the parameter that sizes its
counterweight coupling (`pulley_radius` / `length_counterweight`), and `optimization.param_names(machine)`
swaps it into the five-name search space. So `OptimizationConfig.machine` is a field of its own,
not a `fixed_params` entry (it decides the search space rather than being searched), and the
CLI/UI both resolve their defaults, bounds and labels through it. In the dashboard every input's
session-state key is scoped to the machine (`_widget_key`): Streamlit keeps a keyed widget's value
across reruns, so a box can only be re-defaulted by becoming a different widget - the same trick
the length inputs use across the unit toggle - the optimizer target and its search weights
included, so a machine's target distance and weights are its own. Saved defaults are stored per
machine to match: `user_defaults.json` holds a `machines` map, so each machine keeps its own
optimizable values, ranges, fixed geometry and target block, and saving one leaves the other's
alone; the top-level `machine` key is only which was saved last, i.e. which the dashboard opens
on. `_saved_machines()` migrates the original one-machine file - sections at the top level beside
a single `machine` key - by reading them as that machine's block, and the next save rewrites it in
the new shape. Both animation frontends draw the linkage from the `cw_pin`
track that `sample_component_positions()` returns, and skip the pulley disc when there is none.

The Docker image (multi-stage, non-root, healthcheck) installs the wheel with the `[fast]` extra and starts via the `trebuchet-web` console script; deps are pinned in `docker-constraints.txt`. Saved dashboard defaults go to `TREBUCHET_DATA_DIR` (run.py sets the repo root, Docker sets `/app/data`, bare `trebuchet-web` falls back to `~/.trebuchet-sim`).

The ground is a hard stop for the beam: `_first_arm_ground_angle()` is the arm angle at which whichever end of the beam is lower first touches down (the tip where `sin(theta) = -pivot_height/arm_length`, and on the traditional machine the short end behind the pivot), and reaching it ends the launch with no release, in both engines. The event is on the *angle*, not on the beam's clearance, and deliberately: clearance dips below zero and comes back within a fraction of a turn, so a solver testing its sign at step endpoints steps clean over the excursion - which is exactly what happened during slack stretches, where the machine is a smooth pendulum and RK45 stretches its step past the width of the dip. It binds, and the defaults are set so that it binds on paper rather than in practice: `PARAM_BOUNDS` caps the arm at 2.0 m and both machines' default `pivot_height` stands above that (2.5 m on the pulley machine, 2.6 m on the traditional one), so a search run with the shipped defaults cannot return a beam that digs itself in. It reached that shape the hard way. The pivot used to default to 1 m against a 2.5 m arm bound, which left all but the bottom 40% of the range unbuildable and parked the optimizer's arm against the pivot instead (0.999 m at a 1 m pivot, 2.000 m at 2 m); raising the pivot is what buys the range back, and capping the arm is what keeps the bound honest about what it will return. Measured best-of-16-seeds, the cap costs 1.4-7.4% of maximum range at the 2.5 m pivot (a pulley machine reaches 105.9 m with the snap penalty active against 107.4 m uncapped, and 181.7 m against 190.5 m without it), while holding the cap and raising the pivot from 1 m to 2.5 m buys 13% (93.8 m to 105.9 m). The curve flattens right where the default sits: 105.0 m at a 2 m pivot and 107.6 m at 4 m, with the winning arm stuck at about 1.65 m throughout, which is the ground having stopped deciding the design. `PARAM_LIMITS` still reaches 10 m for anyone who stands their machine taller to match.

For the projectile the ground is not a stop but a surface it can rest and slide on, which is where the launch's other two regimes come from (see physics.py above). `ground_start_state()` is the loading pose: where the cocked tip stands no higher than the sling is long, the projectile does not hang from it at all but lies on the ground at the far end of the sling, laid back on the side the tip leans towards - away from the throw. That is the traditional machine's own default geometry, whose hanging pose put the stone 23 mm underground. Which regime the launch then starts in is read off the constraint forces at that pose rather than assumed, so a sling that would snatch the stone up immediately starts airborne instead of spending a zero-length segment in contact. `simulate()`'s efficiency divides by the potential energy the launch spent, so the projectile's share of it is measured from where the projectile actually starts, not from the hanging pose. The counterweight still has no launch-phase ground contact.

Simulation results use the convention: `"error" in result.metrics` means the run failed; `metrics["release_occurred"]` False means the arm never reached the release angle - either it ran out of `t_max` or `metrics["arm_ground_contact"]` says the beam struck the ground first, and `metrics["simulation_time"]` is when the launch actually ended rather than `t_max`. Check both before rendering animations or reading release metrics. A launch that touched the ground is not a failure and has no flag of its own: `projectile_ground_contacts` counts landings and `projectile_ground_fraction` the share of the launch spent resting on it, and the two are independent - a machine loaded on the ground starts with a nonzero fraction and no contacts, while a stone that touches down and is snatched straight back up records a contact and no fraction. Only a contact is a fault worth warning about, which is what the CLI and dashboard key their warning on.
