# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Setup, from any Python - builds .venv/ and installs the project into it.
# Also the repair step after this folder is copied or synced to another machine.
py bootstrap.py
.venv\Scripts\activate

# Run all tests / a single test
python -m pytest
python -m pytest tests/test_physics.py -k test_name

# Launch the Streamlit web UI (opens browser at localhost:8501).
# Rebuilds .venv automatically if it is missing or stale, via bootstrap.py.
python run.py

# CLI simulation and optimization
trebuchet simulate --arm-length 0.813 --animate
trebuchet optimize --target-distance 30 --lock counter_weight_mass=14
trebuchet optimize --target-distance 30 --threads 8   # cap the cores the search uses
```

There is no linter configured. Saved CLI outputs (GIFs, plots) land in `outputs/` (git-ignored).

`bootstrap.py` is the one setup path, and it is also where the venv's portability is
written down, because only one part of that is fixable. `pyvenv.cfg` names an absolute
`home` outside the project (the base interpreter), and the `Scripts\*.exe` console
wrappers embed an absolute shebang to the venv's own python - neither has a relative form,
which is why a `.venv` copied between the two Windows accounts this repo is synced across
dies with "did not find executable" and has to be rebuilt. What *is* fixable is pip's
editable `.pth`: `bootstrap.relink()` rewrites its absolute path to `src/` as one relative
to site-packages after every install, since site.py resolves a non-absolute `.pth` line
against the directory it was found in - so renaming or moving the project folder on one
machine no longer breaks the install. Copying the project and running `py bootstrap.py` is
the portable operation; copying a built venv is not one, extras and compiled wheels
(numba, scipy) being per-ABI and per-OS regardless of paths. Prefer `python -m pytest`
over bare `pytest` for the same reason - it goes through the interpreter rather than the
absolute-shebang wrapper.

## Architecture

Python package under `src/trebuchet_sim/` (src-layout, installed editable). The core dataflow:

`config.TrebuchetParams` → `physics.TrebuchetSimulator.simulate()` → `SimulationResult` → consumed by visualization, web UI, CLI, and optimizer.

- **physics.py** — Euler-Lagrange dynamics of the launch phase (state = `[theta, theta_dot, alpha, alpha_dot, psi, psi_dot]`: arm angle, sling angle, and the counterweight's swing about its pin), integrated with `scipy.solve_ivp` until the release event fires. `release_angle` is the *pin* angle - the sling measured from the arm, `beta = alpha - theta` - not the arm's angle in the world, which is what it used to be. A trebuchet releases when the ring on the sling's free cord slides off a pin fixed to the arm tip, and that pin turns with the arm: what it can sense is the sling's direction relative to the arm, and nothing on the machine can sense where the arm points in the world. The distinction is not academic - under the old convention the shipped pulley design reached its release arm-angle on the sling's *third* pass, so a pin built to it would have fired on the first, at 11.35 m/s pointing backwards against the 17.6 m/s the model claimed. A pin has no idea how many turns anything has made, so `_release_target` re-anchors the target per taut segment onto the copy of the pin angle just below where the sling actually is - alpha is rebuilt from an arctangent every re-entry, so its branch is an accident of the geometry at that instant - the same trick `_first_arm_ground_angle` plays on the beam. And the release is armed in `TAUT` alone: a pin can only let go of a sling it is holding under load and swinging free, so a slack sling, or a taut one dragging a stone along the ground, runs on until the sling picks the stone up again. Produces `SimulationResult` with `distance`, `efficiency`, a `metrics` dict, the `LaunchSolution`, optional energy history, and the post-release `trajectory`. The sling is modeled as a real rope: when the rigid-link tension would go negative the projectile detaches (`LaunchSolution` stitches taut/slack segments) and the re-tension snap dissipates energy, reported as `string_slack_fraction` / `sling_snap_count` / `sling_snap_energy`. Those three only fire once the sling has *already* let go, so `sling_tension_deficit` grades the approach as well: the share of the launch the sling spent below `config.SLING_TENSION_FLOOR` projectile weights, weighted by how far below, clamped to [0, 1] and never less than `string_slack_fraction`. It is the optimizer's only continuous handle on jerk - see `snap_penalty_weight`. What carries the counterweight differs between the machines, and so does what a negative tension in it means. The pulley machine hangs its weight on a rope over the axle, which the model holds rigid; a rope cannot push, so a negative tension there is unphysical and is charged as `cw_rope_compression_impulse` (the integral of max(0, -T) dt, N*s), with the web UI and CLI warning above the 0.05 N*s noise floor. The traditional machine has no rope anywhere in that linkage - the weight is pinned to the arm's short end - and a pinned two-force member is a strut, which carries compression as readily as tension. So that machine's impulse is identically zero and nothing is charged for it; `min_cw_rope_tension` is still reported on both, because on the traditional machine a negative value is a member load to size for rather than a run to discard. `_cw_link_tension` is the one place either machine's answer comes from: the pulley machine's weight travels straight down, so its rope reads `m(g + r_pul·θ̈)`, while the traditional machine's is a point mass on a massless pinned link — a two-force member, so its tension is that mass's radial equation, `m(l_w·ψ̇² + l_cw(θ̈·sin(ψ−θ) − θ̇²·cos(ψ−θ)) − g·sin ψ)`, which is exactly `mg` at rest. This reading has moved twice, and both moves are worth keeping. The metrics were pulley-only; then they were charged on both machines, on the argument that a pin holds the link's *end* rather than its length and the weight hangs a further `counter_weight_rope_length` below it. That argument is right for a rope hanger and wrong for this machine, which is pinned right through - so they are pulley-only again, deliberately this time. Charging it was not free: it scored out designs like the one in tests/test_traditional.py that drives its link to -900 N, which is a strut load a builder sizes for rather than a run the model cannot represent.The ground is the second one-sided constraint, and it is independent of the sling's, so a launch is a stitched walk through four regimes rather than two - `TAUT` / `SLACK` / `TAUT_GROUND` / `SLACK_GROUND`, since a sling can go slack over a projectile already lying in the dirt and a taut one can drag a projectile along it. `TAUT` keeps the six-component state; the other three carry the projectile explicitly as `[theta, theta_dot, px, py, pvx, pvy, psi, psi_dot]` with the grounded pair pinning `pvy` to zero and `py` to the resting projectile's own centre height - its radius, not y = 0 - so a resting projectile stays exactly on the line instead of drifting off it. `TAUT_GROUND` is the one regime where both constraint forces are live: `grounded_forces()` solves the sling tension alongside the accelerations, so the sling letting go and the projectile lifting off are each just one of them reaching zero. Landing costs energy - `_apply_ground_impulse` takes the projectile's downward momentum and the sling's share of the jerk together, since a landing on a loaded sling is felt by the arm - reported as `projectile_ground_fraction` / `projectile_ground_contacts` / `projectile_ground_energy`. The pivot's dry bearing friction is the one loss that scales with how far the arm turns rather than with how fast: `mu*N*r_shaft` whatever the speed, from `bearing_friction_coefficient` (0.2, steel on dry hardwood) and `pivot_shaft_radius` against the static bearing load, which is `total_mass` on either linkage. It is regularized as `tau*w/sqrt(w^2 + eps^2)` (`config.PIVOT_FRICTION_SMOOTHING`) rather than left as a sign function an adaptive integrator has to chase - smooth, full magnitude within a few eps, and exactly zero at rest, so a machine at t=0 is not handed a friction torque with an arbitrary sign. What it does not model is stiction. It is charged per radian, which is what the shipped pulley machine had most of, and re-deriving against it cut that machine's rotation from 287 to 238 degrees. The post-release slack aftermath uses a second, *unloaded* magnitude: once the counterweight is lying on the ground it is not bearing on the pivot any more, and without that the bare arm - a hundredth of the machine's inertia - is left fighting the whole machine's friction and stops dead in a few hundredths of a second. Aerodynamic drag on the beam is a torque integrated along it, 1/8·ρ·Cd·w·L⁴·θ̇² per side of the pivot; it was 1/6·ρ·Cd·w·l_a³ - that integral without the moment arm, which is the beam's total drag *force* - so it was short a length, not a torque at all, and wrong by a factor that moved with the arm length the optimizer was choosing (3.1x too large on a 0.43 m arm, 0.74x on a 1.8 m one) while ignoring the traditional beam's short end entirely. The two compression impulses and the tension deficit are carried as ODE state components (`N_QUADRATURE = 3`) on the end of every regime's state vector, not summed afterwards. As a trapezoid over the accepted steps they were second-order quadratures on a grid the integrator had sized for the fifth-order dynamics, and worse, their integrands have kinks - at zero tension, and at the deficit floor - that the dynamics do not, so the step grid was blind to exactly the features carrying the value: between rtol 1e-6 and 1e-10 the deficit moved by up to 0.021 and the counterweight impulse by 6.9%, which at the shipped penalty weights is 21 and 100 cost units, a 2% and a 10% miss on the target distance out of integration noise alone. As states they are advanced by the same fifth-order weights as everything else and their error is measured, at their own `QUADRATURE_ATOL` of 1e-7 rather than the 1e-6 the physical states get - they start at exactly zero and the counterweight's is a narrow spike over an otherwise flat launch, so the demand belongs against what they are worth. That costs 60% more accepted steps (21 to 34 on the shipped launch) and settles the counterweight impulse from 8.7e-4 N*s apart at atol 1e-4 to 2e-5, and the deficit from 2.3e-3 to 3e-6. Every state map restarts them at zero, so no interval spans a snap and the launch's total is the sum over segments; the one crossing that carries the physical state over untouched - `TAUT_GROUND` to `SLACK_GROUND`, where nothing is impulsed and the projectile simply stops being pulled - has to restart them by hand, and not doing so drove one traditional draw's deficit to 1.156 on a metric whose whole meaning is a share of the launch. `simulate_aftermath()` runs the post-release machine on its own clock and takes the counterweight's swing at release along with the arm's: psi is a live coordinate on the traditional machine and the launch leaves it mid-swing, so restarting it at the resting pose - which is what happened before it was passed - teleported the weight 323 mm the instant the projectile left, in the animations and in the dynamics after.
- **trajectory.py** — ballistic flight after release with quadratic air drag. Shared so the sim engine, matplotlib animation, and web animation all render the identical flight. Its `ground_level` is the height of the projectile's *centre* when it rests on the ground - the sphere's own radius, the same line the launch phase holds a grounded projectile on - so a stone that leaves the sling low lands where it would have lain rather than sinking one radius further in. A release at or below that line has no flight to integrate at all and returns a `solution` of `None`: asking for one would leave the impact event with no downward crossing to find and run out the clock.
- **`sample_component_positions()`** in physics.py samples projectile/arm-tip/counterweight positions from a solved run; both animation frontends (matplotlib and Three.js) build frames from it so they can never disagree with the physics. It and the energy history read the launch through `LaunchSolution.full_state()`, which resolves a segment and evaluates its interpolant once per instant: the per-quantity accessors beside it each do their own, and a sampler wanting all three paid three times over - 41% of a `track_energy` run.
- **visualization.py** — the matplotlib frontend: the CLI's dual-view animation and `build_energy_figure`, which the dashboard embeds directly (`compact` for the one-screen layout, `dark` applied to a finished figure rather than through rcParams, so the CLI's saved PNGs are untouched). No physics of its own - frames come from `sample_full_timeline`, the energy panels plot `SimulationResult.energy_history` as recorded.
- **optimization.py** — differential evolution over the five optimizable params (`PARAM_NAMES` / `PARAM_BOUNDS`). The objective penalizes the pulley machine's counterweight-rope compression impulse (`slack_penalty_weight`, mirrored in both engines) so the search only returns solutions where that rope stays in tension; the traditional machine reports zero there by construction and is charged nothing, its weight being pinned to the arm on a strut. It separately penalizes `sling_tension_deficit` (`snap_penalty_weight`, also in both engines, exposed as `--snap-penalty-weight` and as the dashboard's Tuning popover "Snap penalty"). The two are not redundant: an impulse is identically zero until a rope has let go, so it is a wall and not a gradient, and DE parked on the cliff edge without the deficit term. A third, `jerk_penalty_weight` (`--jerk-penalty-weight`, "Impact penalty"), charges per joule of `sling_snap_energy` + `projectile_ground_energy` — the jerks that have already happened, which both engines had always measured and the objective had only ever seen through `efficiency`, where a joule lost to a stone hitting the dirt prices exactly like a joule lost to air drag. It is identically zero for a design that neither snaps nor lands, so with the shipped pivot heights it moves nothing; it bites on forced geometry, where a pulley machine on a 0.6 m pivot used to reach 45 m by driving the projectile into the ground and paying 17.2 J for it. Over 30 problems spanning both machines, the joules the winners throw away run 47.1 / 9.9 / 1.3 / 0.3 at a weight of 0 / 5 / 20 / 100, with mean efficiency and target accuracy flat throughout. The objective's weights are calibrated against a benchmark whose targets are 40/70/95% of the range each machine can reach *with the snap penalty active* - a machine is allowed to throw far further by wrecking its own sling (a plain pulley machine reached 182 m limp against 106 m loaded at the defaults of the time; the traditional machine pays nothing for the same promise), so targets drawn from the unprotected range would be unreachable by anything worth building. Against those, `distance_weight` 10 against `efficiency_weight` 5 lands within 2% of the target every time, where the old 1 hit 37% and missed by a median 17.9%; `snap_penalty_weight` 1000 over 300 buys a 20x lower tension deficit for 0.008 of mean efficiency. Two rules sit in front of the integration rather than in the weights. A sling longer than 0.95 of its arm is refused outright, but only on the **pulley** machine: that machine cocks with the sling tucked alongside the arm, so a sling near the arm's own length has nowhere to lie and the pose stops describing anything buildable. The traditional machine lays its sling out from the tip to a stone on the ground (or hanging), and a real one is commonly slung as long as its long arm or longer, so nothing couples its two lengths - its sling is bounded by the search range alone (`PARAM_BOUNDS` / `param_bounds`, reaching `PARAM_LIMITS`' 10 m), and widening it means widening that range rather than lengthening the arm to earn it. The second is `config.MAX_PHYSICAL_EFFICIENCY`: efficiency is the projectile's kinetic energy over the potential energy the launch spent, which energy conservation caps at 1, so a launch reporting meaningfully more has a collapsed denominator - it spun up without the counterweight descending. That is not a harmless bad number, because the objective *maximizes* efficiency: one seed in 16 on the traditional machine used to win outright with a design measuring 3.5e15 efficiency and scoring -1.76e18, a 0.58 m arm on a 0.13 m sling that the fast engine threw 2516 m and the reference never released at all. Both engines refuse it now, and the shipped defaults are untouched by the guard.

`optimize_trebuchet` raises rather than returning when every design scored `INVALID_COST`. A search like that has a perfectly flat landscape, converges on it, and leaves `de_result.x` wherever the population was standing - which reached the dashboard as a panel of blank metrics and a log of empty rows, with no way to tell "here is the best machine" from "there was no machine". The message quotes the pivot, the locks and the narrowed ranges back, because one of those is always what has to move.

Three parameter tiers matter throughout the codebase: *free* (optimizer searches, between `PARAM_BOUNDS` or a `param_bounds` override), *locked* (user pins an optimizable param), *fixed* (`fixed_params` — never optimizable, e.g. pivot height, projectile mass). Two bounds tables, not one: `PARAM_BOUNDS` is the default search range and `PARAM_LIMITS` the envelope a `param_bounds` override may move within, so a range can be widened past the defaults as well as narrowed. `release_angle`'s entries in both moved when it became the pin angle (see physics.py above): the search range is -90 to 150 degrees and the envelope a full -180 to 180, which is about where a pin can usefully sit rather than about how far the arm turns - the upper end under the tightest cocked sling-to-arm angle either machine starts at, since a pin above where the sling already is cannot catch it without a whole extra turn, and the lower end past full extension where a sling swung out in front of the arm throws flattest. `OptimizationConfig.seed` is 33 rather than the old 572956 because the pulley machine's landscape has one narrow basin well below the broad one around it: over 48 seeds at the 30 m target, 40 converge on a 1.0 m arm releasing at a -69 degree pin for 73.5% efficiency and score about -235, and the 8 that find the narrow one get a 0.37 m arm at about a -4.2 degree pin, 90.1% efficiency and about -282.7. This is not quite that machine's best of the 8 (-282.636 against -282.833), because one seed has to serve both: on the traditional machine 46 of the same 48 seeds return a design both engines agree on and those land within about 0.005 of a single score, and this seed is among them where the pulley machine's own best is 0.36 adrift. A locked parameter's range is unused rather than an error, because the dashboard carries one for every parameter regardless of its lock. `fastsim.py` models both linkages *and* the same rope-sling launch physics.py does, so neither the machine nor the trajectory decides the engine any more; its state carries the counterweight swing on both, matching physics.py's layout so the two take the same step path rather than merely solving the same equations. Pure computation, no printing; cli.py is the presentation layer.
- **config.py** — `TrebuchetParams` dataclass; derived quantities (masses, moments of inertia, areas) are properties. `DEFAULT_OPTIMIZABLE_PARAMS` is the single source of defaults shared by CLI, web UI, and tests, and is optimizer output for the 30 m target on the shipped weights and seed - so it is re-derived whenever the physics or geometry it was searched against moves. It was, when `pivot_height` rose to 2.5 m (the pulley machine's equations of motion do not contain the pivot height, so the old set launched identically and simply released 1.5 m higher, overshooting to 31.37 m), again when the arm's drag torque was corrected (the old coefficient was short a factor of length and overstated the drag on a 0.43 m arm by 3.1x, so the search had been buying its way out of air resistance the machine does not have), and again for two modelling changes and two engine fixes at once: `release_angle` becoming the pin angle, the pivot's dry bearing friction, the sling-circle guard in fastsim, and the objective's caching bug. The current pulley set reads 73.2% efficiency, against 74.8% for the set derived under fastmath and 90.1% for the one before the beam was solid - each drop is the model charging for something it used to give away, not the machine getting worse. It holds its counterweight rope in tension throughout, bottoming out at +0.57 N, where those two sets pushed it to -0.77 N and -93.0 N. That is not the price of the efficiency, though: raising `slack_penalty_weight` does not drive the search back to the broad 1.0 m basin, it finds the same short arm with the compression nearly gone at the same range and efficiency (best-of-16-seeds reads 0.0216 / 0.0023 / 0.0008 / 0.0002 N*s at a weight of 200 / 800 / 2000 / 2500, with efficiency flat at 90.0-90.4%). The shipped 200 is simply not asking; it is left alone because the defaults are defined as what the documented command returns on the *shipped* weights, so moving it is a calibration decision about every search rather than about those five numbers. `DEFAULT_TRADITIONAL_PARAMS` is derived the same way, for the same target and seed, against `DEFAULT_TRADITIONAL_FIXED`; it reads 93.4% and throws in a single taut segment, its sling never going slack and its stone touching neither ground nor beam. Both are now checked against *both* engines before being shipped, because one traditional seed returns a far better score on a design fastsim throws 30 m and physics.py throws 0 m - the sling's tension dips to -0.024 N for 7 ms, fastsim resolves the dip and goes slack, and scipy straddles the whole excursion with a single 14 ms step. A design whose distance depends on which engine you ask is not a default, whatever it scores. `MachineType` picks the counterweight linkage: `PULLEY` (weight on a rope over the pivot axle, constant lever `pulley_radius`, single-sided arm) or `TRADITIONAL` (weight pinned to the arm's short end `length_counterweight` behind the pivot, so it swings on its own coordinate and the beam has mass on both sides — see `arm_cm_offset` / `moi_arm`). One set of equations of motion covers both; `has_pulley` branches the handful of places they differ. `initial_arm_angle` is the arm's angle in the world on the ordinary convention: zero points from the pivot straight out along +x - horizontal, level with the pivot, and downrange - and positive turns counter-clockwise, raising the tip. Both machines throw toward +x, so zero means the same thing on each, and the whole convention lives in the one expression `tip = (l_a*cos(theta), l_a*sin(theta) + h_T)`. It is not `release_angle`, which since becoming the pin angle is measured from the arm to the sling and not in the world at all. `initial_arm_angle` defaults to `None` and `__post_init__` resolves it through `resolve_initial_arm_angle`. Both machines' cocked angles are constants (`DEFAULT_INITIAL_ARM_ANGLE`): 45 degrees on the pulley machine, -135 degrees on the traditional one - long arm down and behind the pivot, counterweight raised in front. The traditional machine's used to be *solved* rather than chosen, by walking the long arm down until its own tip was 50 mm off the ground, and that had the wrong body touching the ground. A trebuchet rests its **projectile** there and holds the beam clear, and where the stone goes is already solved properly by `physics.ground_start_state` - the sling is a circle about the cocked tip, the ground is the line the resting stone's centre lies on, the stone starts where they meet, and when the two do not meet the sling simply hangs from the tip. Nothing in that needs the beam near the ground. Deriving it from the beam also broke machines that were otherwise fine: the arcsine had no solution once the pivot outstood the arm, and the clamp then returned -pi/2, straight down, where every gravity torque carries a cos(theta) and is identically zero - the machine parked on its own balance point, throwing nothing. With the arm capped at 2.0 m that made *every* traditional design on a pivot of 2.2 m or more score `INVALID_COST`, so a search there had a perfectly flat landscape to converge on and returned whichever design the population was standing on; at a 2.6 m pivot the same machine now launches normally, with the stone hanging from the tip instead of lying on the ground. `DEFAULT_TRADITIONAL_FIXED` keeps the 1.0 m pivot, but as a choice rather than a consequence - swept at 1.0 / 1.4 / 1.8 / 2.2 / 3.0 m the share of the search box that scores runs 13 / 27 / 29 / 30 / 31% and the best score -456.3 / -456.7 / -457.4 / -457.4 / -458.7, flattening by about 2 m, so the low frame is within 0.3% of anything taller and is the machine worth describing: at 1.0 m the cocked tip stands 0.484 m up, low enough that the sling reaches the ground and the stone is *loaded on it* rather than dangling. What the pose does cap is the arm: at -135 degrees the tip sits at `l_a*sin(-135) + h_T`, so an arm longer than `h_T/0.7071` (1.41 m here) starts underground and `physics._cocked_beam_clearance` refuses it outright. Since the angle is a constant rather than a function of the arm, the optimizer no longer has to derive it per individual - but `config.AUTO_INITIAL_ARM_ANGLE` remains the "caller did not pin one" sentinel that tells fastsim to resolve the machine's own default, a huge finite value rather than NaN - once forced, because `fastmath=True` let LLVM fold an `isnan()` test to False, and kept now that fastmath is off because a sentinel no compiler flag can break is worth more than one that has to be re-checked whenever the flags move. Typing a value into that box pins the pose instead, which is a real thing to want and is why the box exists; what it also makes reachable is a cocked pose with the beam already underground, which `physics.TrebuchetSimulator.simulate` now refuses outright (see `_cocked_beam_clearance`). `counter_weight_rope_length` resolves per machine too, through `initial_cw_rope_length`; one wrap of the pulley, or the traditional machine's own short arm. It used to be one wrap either way, which sized a pinned counterweight's link from `pulley_radius`, a parameter that machine does not have and whose default moves whenever the *pulley* machine's defaults are re-swept. The traditional defaults used to be a hand-chosen 50 kg / 0.35 m / 1.8 m beam whose release angle alone had been swept, for a machine loaded the way a real one is - tip one sling length up, so the stone lies on the ground at the far end of a sling stretched back behind the pivot. That machine reached its 70.2 m only by driving the counterweight link to −158 N, i.e. by pushing on a rope, which nothing measured at the time (see physics.py above). Holding the beam and pulling the release angle back to where the link stays loaded cost 16% of its range; re-deriving the machine instead hit the 30 m target at 96.8% efficiency on a third of the mass, with every link loaded throughout - the set that has since been re-derived again, above. With the cocked angle a chosen -135 degree pose, the shipped traditional machine loads its stone on the ground and then lifts it straight off: the sling is already carrying enough at that pose that `_settle_grounded` opens the launch airborne, `projectile_ground_fraction` is exactly zero, and the whole throw is one `TAUT` segment. That is new - every traditional launch used to spend part of itself in a grounded regime by construction, because the old pose laid the sling out along the ground. tests/test_ground.py carries dedicated geometries for both poses regardless.
- **fastsim.py** — the Numba engine behind the optimizer's objective, and a port of `physics.py` rather than a simplification of it. It runs the same stitched launch through the same four regimes: taut segments (the Dormand-Prince tableau unrolled into scalars, the hot path a converged design spends its whole launch in) alternating with the three eight-component ones - slack, and the two grounded - which share a single array-based stepper (`_integrate_eight_segment`) branching on a regime code, so there is one readable copy of the tableau rather than three more; joined by the same inelastic `_apply_snap` and `_apply_ground_impulse`. It used to hold the sling rigid and lean on the objective's penalties to keep the search where that lie did not matter, which left the engines a median 56% apart on distance once a sling let go, and let a search pushed hard on distance win on throws only the rigid model believed in. The ground was the same story a step later, and it was closed the same way. They now agree to a median 0.0066% on distance across launches carrying a discontinuity and 0.0012% across quiet ones, and to 0.003% on the energy the ground takes (`tests/test_fastsim.py` measures this over both machines, classifying a launch by whether it contained any discontinuity at all rather than by slack alone - a landing is one too). The two also open every segment on the same step grid: `_initial_step` / `_probe_step` port scipy's `select_initial_step`, where this engine used to start each segment at a fixed 1e-3, and over a short segment that choice is the whole sample. That was the last loose metric's cause - the counterweight rope's compression impulse is a trapezoid over a spike, and it was held to 30% and a 0.25 N*s floor against a fixed opening step; every draw in the sweep that carries any impulse now agrees to better than 0.7% on the pulley machine and 0.5% on the traditional one, from 0.038 N*s to 66.9. (`_cw_link_tension` is ported here too, so both machines' counterweight links are *measured* in both engines; only the pulley machine's is graded, since only it has a rope.) Agreement is still not convergence, and this is the metric where the difference shows: below about 1 N*s neither engine's value is converged - the reference reads 0.635 / 0.571 / 0.605 at rtol 1e-6 / 1e-8 / 1e-12 on the draw that motivated the port, where this engine reads 0.639. It feeds a feasibility term, so what has to agree is that the design is charged out of contention. The three running integrals are states here too, on the end of both layouts and inside the error norm, so the two engines still open and walk every segment on the same grid. One thing this engine has that the reference does not is a guard on the sling circle: a rope cannot stretch, so while the sling is slack the projectile lies inside the circle it sweeps, and a step that ends outside is simply too long and is rejected the way a failed error test is. Every slack segment opens exactly on that surface, which leaves the ordinary "was positive, is now negative" test nothing to arm on, and the first step is sized by a smooth pendulum plus a free-flying stone: on a traditional draw whose tension grazes zero at -0.013 N the stone leaves the circle by 1.3 micrometres for 13 milliseconds, and the step that spans that was accepted - the stone escaped, flew for a second, landed 1.79 m outside its own sling, and a launch that should have thrown 1.4 m threw nothing. Only a segment that opens *on* the circle is guarded (`RETENSION_CIRCLE_SLOP`): one entered from `TAUT_GROUND` opens wherever that regime's constraint drift left it, microns outside rather than at the rounding of zero, and that is a state that started there rather than a step that escaped - rejecting for it stalls the segment instead of answering. The two cases are eleven orders of magnitude apart (2.8e-17 m against 3.8e-6 m), so the band separates them with room to spare. That one was worth finding twice over: it read differently compiled than interpreted, because `fastmath` reassociation moves the last bit the test was keying on, which is the shape a JIT-only bug takes here. Every kernel in this file is compiled with `fastmath=False`, and that is the one flag here worth arguing about. With fastmath on, the same source produced *different physics* depending on whether numba had just compiled it or reloaded it from the on-disk cache: over 8000 designs across both machines, 2286 values moved between a cold run and a warm one - designs crossing between a real score and `INVALID_COST` among them - and so did the optimizer's own answer. A cached function comes back as opaque object code while a freshly compiled one is still IR its callers can inline, and `reassoc` and `contract` then let LLVM reshape the arithmetic differently on the two paths; dropping just those two flags cuts it to 432 values but does not close it, and `fastmath=False` closes it exactly, 0 of 8016. A launch is a stitched walk through regimes whose boundaries are sign tests on constraint forces, so a last-bit difference does not stay one - it decides whether a sling lets go, and everything after that is a different launch. It costs about 8% on the hot path and takes a third off the cold compile - 177s under fastmath against 111s as shipped. That also settled a bug that had been read the other way round for a long time: `_score` and `evaluate_population` were left *uncached* because a cached `_score` reloaded from disk scored a design that throws nothing as -144.9 instead of `INVALID_COST`, and differential evolution returned it as the winner of its seed - which looked like a fault in reloading a caller of a cached function. It was fastmath all along. With the flag off a cached objective is bit-identical to an uncached one, cold and warm alike, so both are `cache=True` again and the per-run compile goes with them: warm startup drops from 5.35s to 0.75s (0.14s of it JIT, against 4.8s before), and `trebuchet optimize` now reproduces its answer to every digit whether the cache is warm or cold - which it did not before, and which is what makes the shipped defaults re-derivable at all. Closing each gap also opened design space the search had been driven out of: the sling port took the pulley machine's measured maximum range from 121.6 m to 191.3 m, and with the snap penalty at its shipped 1000 the ground port took it from 73.6 m to 88.1 m at the 1 m pivot of the time, because designs that were previously mis-scored - flying the stone through the floor - resolve into real ones.
- **web/app.py** — Streamlit dashboard (3 columns: parameter inputs / animation + energy plot / results). Streamlit reruns the whole script on every widget interaction, so expensive outputs (animation HTML, energy figure) are pre-rendered once in `_store_result()` and cached in `st.session_state`. Results render as custom HTML (`_metric_grid` / `_spec_list` / the hero block), not `st.table`. Which of the two a block gets is the page's hierarchy and has been deliberately swapped: the resolved machine geometry takes the cards, because it is what you would take away and build - the optimizer's own choices, and the cocked angle, which on the traditional machine is derived rather than typed - and the launch metrics (release velocity, flight time, projectile KE) take the dense list below, describing how that machine then behaved rather than what it is. The cocked-angle box is `_fixed_input` on the pulley machine (required) and `_fixed_input_optional` on the traditional one, where blank is legal and means "derive it from the geometry" - so `fixed_ready` exempts exactly that one box from the blank-means-still-typing rule. Unit switching: length inputs swap between separate metric and ft/in widgets so they reseed themselves, but the single-box inputs — masses, and the search-range boxes, which use decimal feet rather than a ft+in pair — must be converted in place by `_sync_unit_inputs()` before any input renders. Search ranges live in a popover: two more boxes per row would not fit the left column, and the one-screen layout has no slack. The dashboard carries no tooltips at all - no Streamlit `help=` icons, no native `title=` attributes on the section headers or the animation's own controls - so anything a user needs to know has to be in a label, a caption, or the results panel rather than hidden behind a hover. Removing them took the `help` parameter out of the input helpers (`_si_input`, `_length_pair_input`, `_fixed_input_optional`, `_optimizable_input`) and the help column out of the design-variable `rows` table, so re-adding one is a deliberate act rather than a spare keyword nobody notices. Whether a range counts as customized is decided at the box's own display precision (`INPUT_DECIMALS`), since a default that has been through a unit conversion and back no longer equals itself in SI. Imperial is the default unit (the toggle's `value=True` seeds only the first render, so switching to metric sticks for the session); tests that address boxes by label pin the toggle rather than hardcoding either unit - see `tests/test_web_defaults._metric`. Errors carrying structured lengths are re-rendered here in the page's own unit rather than printed as the SI sentence physics.py builds, so a ft/in dashboard is not told to raise its pivot to "1.49 m".
- **web/theme.py** — the design system, and the single source of truth for the dashboard's look: palette constants, `streamlit_theme_env()` (Streamlit resolves its theme at server start, before the app script runs, so it can only arrive via env vars — applied by both `web/launcher.py` and `run.py`, which is why the container and a local checkout match without a `.streamlit/config.toml`, a path that is git-ignored), and `DASHBOARD_CSS`. The layout is a fixed-viewport flex column: the page is pinned to `100vh` and the panels that should absorb slack are marked `flex: 1 1 0`, replacing the previous `calc(100vh - Npx)` magic numbers that had to be re-measured by hand and had already drifted far enough to push the header off-screen. Imports nothing, so `run.py` can read the palette before the package is installed.
- **web/animation3d.py** — no physics: samples the solved result into a JSON timeline (`_build_timeline`) and embeds a self-contained Three.js HTML page that plays it back with scrub/speed controls. The HTML template is a Python string with `__TIMELINE_JSON__` / `__HEIGHT__` / `__THREE_JS__` / `__ORBIT_JS__` placeholders plus the palette placeholders in `_THEME_SUBSTITUTIONS` (so the scene shares `web/theme.py`'s colors); Three.js r128 is vendored in `web/static/` and inlined so the animation works offline (r128 pinned deliberately — newer releases removed `examples/js/OrbitControls.js`).

Selecting a machine touches every layer, because the two differ in one design variable rather
than in a setting: `config.LINKAGE_PARAM` maps each machine to the parameter that sizes its
counterweight coupling (`pulley_radius` / `length_counterweight`), and `optimization.param_names(machine)`
swaps it into the five-name search space. So `OptimizationConfig.machine` is a field of its own,
not a `fixed_params` entry (it decides the search space rather than being searched), and the
CLI/UI both resolve their defaults, bounds and labels through it. In the dashboard every input's
session-state key is scoped to the machine (`_widget_key`): Streamlit keeps a keyed widget's value
across reruns, so a box can only be re-defaulted by becoming a different widget - the same trick
the length inputs use across the unit toggle - the optimizer target and its search weights
included, so a machine's target distance and weights are its own. Saved defaults are stored per
machine to match: `user_defaults.json` holds a `machines` map, so each machine keeps its own
optimizable values, ranges, fixed geometry and target block, and saving one leaves the other's
alone; the top-level `machine` key is only which was saved last, i.e. which the dashboard opens
on. `_saved_machines()` migrates the original one-machine file - sections at the top level beside
a single `machine` key - by reading them as that machine's block, and the next save rewrites it in
the new shape. Both animation frontends draw the linkage from the `cw_pin`
track that `sample_component_positions()` returns, and skip the pulley disc when there is none.

The Docker image (multi-stage, non-root, healthcheck) installs the wheel with the `[fast]` extra and starts via the `trebuchet-web` console script; deps are pinned in `docker-constraints.txt`. Saved dashboard defaults go to `TREBUCHET_DATA_DIR` (run.py sets the repo root, Docker sets `/app/data`, bare `trebuchet-web` falls back to `~/.trebuchet-sim`). Both compose files pass `TREBUCHET_NUM_THREADS` through, defaulted to empty - which every reader treats as "unset", so the container runs one thread per core it can see unless a host sets it.

How many cores the search uses is `OptimizationConfig.threads`, which is *not* `workers`: `workers` is the scipy fallback's process count and does nothing when the fast engine runs, because that engine scores a whole generation in one call and spreads it over numba's thread pool inside `evaluate_population`'s `prange`. So they are two settings for two engines rather than one knob spelled twice. `--threads N` sets it per run and the dashboard reads `TREBUCHET_NUM_THREADS`; the count is restored afterwards, being process-wide state a second run would otherwise inherit. The ceiling is the harder half: numba fixes how many threads a process may ever use when it is *imported*, so `set_num_threads` can only move within it and a request above it is clamped and reported rather than silently dropped. Raising it past the core count is `TREBUCHET_NUM_THREADS`' other job - `fastsim._seed_thread_ceiling()` reads it before the numba import for exactly that reason, and only ever raises, since lowering the ceiling there would cap every later per-run request too. Measured on 16 cores, a generation scores 5.9x faster at 16 threads than at 1 on a large population; the gap to linear is load imbalance rather than overhead, an invalid design returning instantly where a valid one integrates a whole launch, against `prange`'s static chunking. Thread count cannot move a score - `evaluate_population` gives each individual its own slot and never reduces across them - which tests/test_optimization.py asserts bit-exactly, since a count that moved a score would make a run depend on the machine it ran on.

The beam is a contact surface for the projectile as well as a hard stop for itself, and both of the launch's airborne regimes watch for the stone reaching it (`TAUT_BEAM` / `SLACK_BEAM`, `beam_contacts` / `beam_contact_energy` / `min_beam_clearance`). That watch is the one event in either engine that cannot be a sign test at the ends of a step. Every other one crosses zero and stays across; the stone's clearance from the arm dips through zero and comes back, so a step longer than the dip reads positive at both ends and the stone passes clean through the beam with nothing recorded. It is the same hazard `_first_arm_ground_angle` sidesteps by testing the arm *angle* instead of the beam's clearance, except that here there is no monotone coordinate to move onto - the stone's approach is not monotone in anything - so the step is scanned instead, at `BEAM_SCAN_SUBSTEPS` (8) interior points of its own interpolant, in both engines. It was not a rare case: over the 196-launch sweep tests/test_fastsim.py draws, the reference stepped over a real crossing in 5 of 62 pulley launches and 17 of 134 traditional ones, up to 39.7 mm deep, and the fast engine over more; scanning leaves 1 of 62 at 1.14 mm and 0 of 134. `_settle_beam` picks the regime a stone that has just arrived on the arm belongs in, and it has to know which constraint is acting before it asks about forces: a stone that got there out of a slack stretch is somewhere inside the sling circle, and asking `beam_taut_forces` what tension holds a length nothing is holding returns a number, whose sign then sent one launch into `TAUT_BEAM` with the sling 39 mm long against a design length of 697 mm - a state the taut dynamics cannot represent, whose first step drove theta_dot to 1.8e8. So the separation is measured first (`BEAM_SLING_TAUT_SLOP`) and the taut branches are only reachable from a sling actually at full stretch.

The ground is a hard stop for the beam: `_first_arm_ground_angle()` is the arm angle at which whichever end of the beam is lower first touches down (the tip where `sin(theta) = -pivot_height/arm_length`, and on the traditional machine the short end behind the pivot), and reaching it ends the launch with no release, in both engines. The event is on the *angle*, not on the beam's clearance, and deliberately: clearance dips below zero and comes back within a fraction of a turn, so a solver testing its sign at step endpoints steps clean over the excursion - which is exactly what happened during slack stretches, where the machine is a smooth pendulum and RK45 stretches its step past the width of the dip. It binds, and the defaults are set so that it binds on paper rather than in practice: `PARAM_BOUNDS` caps the arm at 2.0 m and the pulley machine's default `pivot_height` stands above that at 2.5 m, so a search run with its shipped defaults cannot return a beam that digs itself in. The traditional machine reaches the same place from the other side, and more firmly: cocked at -135 degrees *both* ends of its beam are at their lowest the instant it is cocked and rise from there, so a machine standing legally at t=0 cannot reach the ground during the throw at all, while one standing low enough to reach it is already underground when cocked and `physics._cocked_beam_clearance` refuses it before the launch starts (see `config.resolve_initial_arm_angle`). Exercising that event on this machine therefore takes an explicitly pinned pose - tests/test_fastsim.py cocks one at -100 degrees with a counterweight arm four times the default. It reached that shape the hard way. The pivot used to default to 1 m against a 2.5 m arm bound, which left all but the bottom 40% of the range unbuildable and parked the optimizer's arm against the pivot instead (0.999 m at a 1 m pivot, 2.000 m at 2 m); raising the pivot is what buys the range back, and capping the arm is what keeps the bound honest about what it will return. Measured best-of-16-seeds, the cap costs 1.4-7.4% of maximum range at the 2.5 m pivot (a pulley machine reaches 105.9 m with the snap penalty active against 107.4 m uncapped, and 181.7 m against 190.5 m without it), while holding the cap and raising the pivot from 1 m to 2.5 m buys 13% (93.8 m to 105.9 m). The curve flattens right where the default sits: 105.0 m at a 2 m pivot and 107.6 m at 4 m, with the winning arm stuck at about 1.65 m throughout, which is the ground having stopped deciding the design. `PARAM_LIMITS` still reaches 10 m for anyone who stands their machine taller to match.

For the projectile the ground is not a stop but a surface it can rest and slide on, which is where the launch's other two regimes come from (see physics.py above). "The ground" for it is the line its own *centre* rests on - one projectile radius up, not y = 0 - and every test the launch makes is against that line: the two landing events, the re-tension over a grounded projectile, the loading pose, the geometry the grounded regimes solve, and the ballistic flight's own impact event (`trajectory.ground_level`). A resting sphere sits on the ground at its radius rather than with its centre in the dirt. `ground_start_state()` is the loading pose, and it is pure geometry with no fallback in it: the sling is a circle of radius `string_length` about the cocked tip, the ground is the line the resting stone's centre lies on, and the stone starts where the two meet - both lengths to the stone's *centre*, so it sits on the surface rather than through it. A circle crosses a line twice and the downrange root is taken, the higher x, on the side the machine throws towards. Only `abs(drop) > l_s` returns None, which is the circle and the line not meeting at all - a pulley machine's tip a metre up on a 24 cm sling - and that is the other geometry rather than a fallback: the sling really does hang. The sign of `drop` used to be a test too, and it silently unloaded the machine: back when the traditional machine's cocked angle was solved by walking its tip to within 50 mm of the ground, a stone of 50 mm radius or more stood taller than the tip it hung from, which is an ordinary stone and was read as "cannot be loaded" - the machine fell back to the hanging pose and started 385 mm underground, with nothing flagged, because a stone that begins below the surface never crosses it going down. The cocked tip is nowhere near the ground now, but a signed drop is still the right shape, since it is what lets one expression solve a tip below the stone's centre and a tip above it. Which root is taken is a design decision rather than a detail: on the traditional machine the cocked tip sweeps back and up, away from a stone laid downrange of it, so the sling is loaded before anything moves and the launch opens in `TAUT_GROUND`, dragging - where the other root had the tip sweeping towards the stone and opening in `SLACK_GROUND`, taking up slack. On the shipped traditional defaults neither root is reached in anger: the stone is laid on the ground, but the sling is already loaded enough to lift it immediately, so the launch opens airborne in `TAUT` and `projectile_ground_fraction` is zero. tests/test_ground.py keeps its own geometries for the dragging and slack-taking poses either way. Which regime the launch then starts in is read off the constraint forces at that pose rather than assumed, so a sling that would snatch the stone up immediately starts airborne instead of spending a zero-length segment in contact. `simulate()`'s efficiency divides by the potential energy the launch spent, so the projectile's share of it is measured from where the projectile actually starts, not from the hanging pose. The counterweight still has no launch-phase ground contact.

The ground is also checked *before* the launch runs. `_cocked_beam_clearance()` is the height of whichever end of the beam sits lowest at the cocked pose, measured to y = 0 (a beam is not a sphere and does not rest on its radius), and a negative value ends the run immediately with an `error`. The beam's own ground event cannot catch this: `_first_arm_ground_angle` finds the first crossing *below* the cocked angle, which for a pose that starts underground is the angle where the beam comes back *up*, so such a launch used to run with its tip buried and the stone hanging a sling length below that - recording no ground contact, because nothing had gone down through the surface. It was unreachable while the traditional machine's cocked angle was derived by walking the arm to the ground, and became reachable when that angle was made settable again; the pulley machine could always reach it with a low pivot and a long arm. The error carries `cocked_beam_depth` / `required_pivot_height` / `cocked_arm_angle_deg` in SI beside the sentence, so a caller showing ft/in can give the same advice in ft/in. The fast engine reaches the same verdict by its own route - such a pose simply never releases - so the optimizer scores it invalid without needing the check.

Simulation results use the convention: `"error" in result.metrics` means the run failed; `metrics["release_occurred"]` False means the sling never reached the release pin angle while the pin could let go of it - the pin is armed in the `TAUT` regime alone - either because it ran out of `t_max` or `metrics["arm_ground_contact"]` says the beam struck the ground first, and `metrics["simulation_time"]` is when the launch actually ended rather than `t_max`. Check both before rendering animations or reading release metrics. A launch that touched the ground is not a failure and has no flag of its own: `projectile_ground_contacts` counts landings and `projectile_ground_fraction` the share of the launch spent resting on it, and the two are independent - a machine loaded on the ground starts with a nonzero fraction and no contacts, while a stone that touches down and is snatched straight back up records a contact and no fraction. Only a contact is a fault worth warning about, which is what the CLI and dashboard key their warning on.
